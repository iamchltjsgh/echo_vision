# 이웃 프라이버시 마스킹 — 서버 마스킹 계약

**2026-08-17 개정 (민선우 리뷰 §3-2 반영)**: 이전 판(ESP32가 사진 촬영 시점에
마스킹)은 폐기됐다. **사진·영상 모두 서버가 마스킹한다.** ESP32는 크롭도
마스킹도 하지 않고 원본을 그대로 올린다 — 이유는 아래 "왜 서버가 하는가" 참고.

이 문서는 좌표가 어디서 나와서(앱) 어디에 저장되고(서버) 어떻게
적용되는지(서버, 사진·영상 둘 다)를 정의한다.

## 왜 서버가 하는가

ESP32에서 JPEG 디코딩·마스킹·재인코딩은 배터리/연산 예산을 초과한다. 사진은
크롭조차 기기에서 서버로 이미 옮겨진 작업이고(민선우 리뷰 §3-2), 마스킹도 같은
이유로 서버 몫이다. 영상(15초, 최대 75프레임)은 그 부담이 프레임 수만큼
곱해지므로 더더욱 기기에서 할 수 없다.

## 설계 원칙

- 카메라는 문에 고정 부착되어 화각이 거의 안 바뀐다. 그래서 촬영마다 AI로 이웃집
  문을 다시 찾는 대신, **설치 시 한 번 지정한 좌표를 계속 재사용**하는 방식으로
  설계했다.
- 마스킹은 **법적 의무가 아니라 권장 사항**이다. 좌표가 없으면(설정 안 함) 그냥
  원본 그대로 처리하면 된다 — 강제하지 않는다.

## 반드시 지켜야 할 것 (가장 중요)

**마스킹 전 원본이 앱이나 외부에 노출되는 경로가 있으면 안 된다.** ESP32가
올린 원본은 서버가 처리하는 잠깐 동안만 존재해야 한다.

- 사진: 업로드 요청 처리 중 메모리에서만 크롭·검사·마스킹하고, **마스킹된
  결과만** `photos/`에 쓴다. 원본 자체를 디스크에 쓰는 코드 경로가 없다.
- 영상: 원본을 `videos_raw_tmp/`에 잠깐 쓰지만, 이 디렉터리를 가리키는 서빙
  라우트가 아예 없고, 처리가 끝나면(성공·실패 무관) **항상** 즉시 삭제한다.
  마스킹된 결과만 `videos/`에 남고 `GET /videos/<filename>`으로 서빙된다.

## 좌표를 다루는 엔드포인트

### `GET /device/mask-regions`

**앱 전용**(설치 모드 재설정 화면이 기존 좌표를 불러와 편집할 수 있게 하는
용도). ESP32는 이 엔드포인트를 호출하지 않는다 — 좌표를 직접 쓸 일이 없다.

응답:
```json
{
  "regions": [
    {"x": 0.62, "y": 0.10, "width": 0.25, "height": 0.55},
    {"x": 0.05, "y": 0.15, "width": 0.20, "height": 0.40}
  ]
}
```

- `regions`가 빈 배열이면 마스킹 없이 원본 그대로 처리한다.
- 최대 4개까지 저장된다(`POST` 시점에 서버가 검증).

### `POST /device/mask-regions`

앱의 설치 모드 화면이 사용자가 지정한 좌표를 저장할 때 호출한다.

### `GET /device/mask-regions/status`

앱 설정 화면이 "현재 마스킹 설정 상태"를 보여줄 때 쓴다.

## 좌표계 — 사진과 영상의 기준 프레임이 다르다 (중요)

사용자는 설치 모드에서 **크롭된 사진**(`GET /photos/<filename>`이 서빙하는,
이미 `(322, 197, 552, 414)`로 잘린 230×217 이미지)을 보면서 가릴 영역을
찍는다. 즉 **저장되는 `x, y, width, height`는 크롭된 230×217 프레임 기준
정규화 좌표다.**

```
pixel_x      = round(x * 230)   # 크롭 프레임 기준
pixel_y      = round(y * 217)
pixel_width  = round(width * 230)
pixel_height = round(height * 217)
```

- **사진 마스킹**: 이미 크롭된 프레임에 적용하므로 위 변환을 그대로 쓰면 된다.
- **영상 마스킹**: ESP32가 크롭 없이 올리는 원본(SVGA 800×600) 프레임에
  적용해야 하므로, 크롭 오프셋을 먼저 반영해 "원본 프레임 기준" 좌표로
  바꿔야 한다. 이 변환 없이 크롭-상대 좌표를 원본 프레임에 그대로 쓰면
  마스킹이 엉뚱한 위치에 찍힌다.

  ```
  full_x      = (322 + x * 230) / 800
  full_y      = (197 + y * 217) / 600
  full_width  = (width  * 230) / 800
  full_height = (height * 217) / 600
  ```

  (`server/app.py`의 `_regions_to_full_frame()` 참고 — 위 식을 그대로 구현한
  것이다.)

- 앱이 저장을 요청할 때 이미 `0.0 <= x, y <= 1.0`, `0.0 < width, height <= 1.0`,
  `x + width <= 1.0`, `y + height <= 1.0`을 서버가 검증해서 거부하므로, 저장된
  좌표는 항상 크롭 프레임 범위 안이라고 신뢰해도 된다.

## 처리 순서

### 사진 (`POST /upload`)

```
ESP32: 촬영(원본, 크롭·마스킹 없음) → 서버로 업로드
서버:  원본 수신 → 크롭(322,197,552,414 → 230×217)
     → 손상 프레임 검사(blank/truncated) → 불합격 시 photos_rejected/에만 저장,
       이벤트 생성 없이 종료(앱에 노출 안 됨)
     → 합격 시 저장된 mask_regions를 크롭 프레임 기준으로 적용
     → 마스킹된 결과만 photos/에 저장, 이벤트 생성·SSE 브로드캐스트
```

### 영상 (`POST /video`)

```
ESP32: 촬영(원본, 크롭·마스킹 없음, SVGA 800×600) → 서버로 업로드
서버:  원본을 videos_raw_tmp/에 임시 저장
     → mask_regions를 위 변환식으로 원본 프레임 좌표로 바꿔 모든 프레임에 적용,
       재인코딩(프레임을 한꺼번에 메모리에 모으지 않고 읽는 즉시 쓰고 버림)
     → 마스킹 전 원본은 처리 완료 직후(성공·실패 무관) 즉시 삭제
     → 마스킹된 결과만 videos/에 저장, video_ready SSE 브로드캐스트
```

`regions`가 비어 있으면(설정 안 함) 사진·영상 둘 다 마스킹 없이 크롭/재인코딩만
해서 저장한다.
